# Containment model

This is the single place that states what "containment" means in Governator, after the Sol redteam repair program (v1.0.0, the first release). Related detail lives in [docs/contracts.md](contracts.md#containment-and-risk-class) (the contract-facing `risk_class`/`docker.*`/`containment.*` fields), [docs/backends.md](backends.md#capability-attestation) (attestation mechanics), and [docs/security.md](security.md) (the finding-by-finding register this model closes).

## The rule

**A local worktree is repository isolation. It is never host containment.** A disposable Git worktree keeps a run's changes out of the live branch until approved; it does nothing to stop a process running inside it from reading or writing anywhere else the host user can. Before the Sol repair, several code paths implicitly treated "runs in its own worktree" as if it were a security boundary — it is not, and no doc, contract field, or code comment should imply otherwise going forward.

What actually qualifies as host containment, for a `risk_class: high` job, is one of exactly three things:

1. **Hardened Docker** — `runner: docker` with `docker.user` (non-root), `docker.read_only_rootfs`, `docker.cap_drop_all`, `docker.no_new_privileges`, a digest-pinned `docker.image` (`@sha256:<64-hex>`, not a mutable tag), and `docker.network: deny`. See [Docker hardening](#docker-hardening) below for what's actually enforced and verified.
2. **Externally enforced local containment** on `runner: local` — Governator's own kernel-level sandbox (Landlock LSM filesystem confinement + a network namespace with no configured route, applied via the hidden `gov __sandbox_exec` re-exec so the restriction is already in force on the process that becomes the backend, not a wrapper it could out-race). Verified by `enforce.Supported()` at launch time. See [Local external enforcement](#local-external-enforcement) below.
3. **A signed operator override** (`containment.override_signature`), ed25519-verified against a configured public key, binding both the job ID and the contract's content hash so neither replay across jobs nor a post-signature contract edit can reuse it.

Everything else — an unenforced local run, a non-hardened Docker config, an expired or missing external-enforcement layer, an unsigned override — fails closed before quota reservation or workspace creation for `risk_class: high` work. `low`/`medium`/`unset` risk classes are scoring-only and are never containment-gated (a `risk_class: medium` *effectful* job is tiered into the same host-containment requirement by default via `containment.local_effectful_tiering`; see [contracts.md](contracts.md#containment-and-risk-class)).

### Why a backend-attested native sandbox is not on this list anymore

Sol redteam v4 finding P0-3 (Session 5) demoted a backend's self-attested native sandbox from "host containment" to "probe-observed evidence." A backend that behaves correctly during attestation probes (right version string, conforming transcript events, "network denied") and then escapes to the host during the real run cannot be distinguished from an honest one by anything the backend itself reports — a program that knows it is being tested can behave only during the test. `gov attest <backend>` still generates and stores an attestation when the backend declares a native sandbox, and the matched attestation's ID still feeds `ExecutionIdentity` (so replay can't reuse one across an attestation change), but `attest.VerifyHighRiskNative`'s verdict **no longer authorizes a high-risk local run**. Only option 2 (Governator's own external enforcement) or option 3 (the signed override) does. The attestation is audit history, not a launch gate.

## What local-worktree isolation actually does and doesn't stop

Local-worktree isolation (every risk class, not just `high`) now additionally enforces:

- **Whole-tree symlink rejection.** Any `runner: local` job refuses to launch if the worktree contains a symlink or junction anywhere outside `.git/`/`.codegraph/` — this closes the path where a tracked symlink (or a symlinked parent of a declared write target) let a nominally "read-only" or scope-limited run write through the link to an arbitrary host path while the post-run fingerprint diff still looked clean. See [docs/contracts.md#local-runner-symlink-containment](contracts.md#local-runner-symlink-containment).
- **Canonical lock identity.** The workspace lock keys on the repository's resolved device/inode identity, not a raw path string, so a symlinked alias to an already-running repository can't slip past the lock and run concurrently against the same tree. See [docs/ledger.md#canonical-workspace-lock-identity](ledger.md#canonical-workspace-lock-identity).
- **Git control-plane fingerprinting.** `.git/hooks` and `.git/config` (resolved to the shared git-common-dir for worktrees, not each worktree's private per-checkout view) are hashed before and after every run, independent of anything the contract declares. A backend process that modifies a hook or the repo config during a run is a blocking violation (`git control-plane mutation`) even though hooks/config live outside the worktree's own file tree and wouldn't otherwise appear in a source diff.

None of these make a local run *contained* — they make it honest about what changed. A process with host-user-equivalent shell access inside a local worktree can still read or write anything that user can; the symlink ban, lock identity, and control-plane fingerprint close specific detection/escape gaps, they don't add a security boundary. That boundary is hardened Docker, Governator's own external local enforcement (Landlock + netns), or a signed override — never a worktree, and never a backend's self-attested native sandbox.

## Descendant containment

A governed local launch (every risk class, not just `high`) wraps its process tree in a descendant-owning primitive (`internal/containment`), so the run's lifecycle can prove extinction before final-state capture rather than treating "the main process exited" as proof nothing is still running:

- **Primitive selection, in order:** `systemd-run --user --scope` (cgroup v2, no filesystem write access needed), then a directly-managed cgroup v2 subdirectory placed via `CLONE_INTO_CGROUP` (`SysProcAttr.UseCgroupFD`), then `unshare --user --map-user=<uid> --map-group=<gid> --pid --fork --mount-proc` as a last resort. The identity uid/gid mapping in the last form keeps file ownership correct; without it the wrapped process would run as `nobody` and silently turn every well-behaved run into a false QUARANTINE.
- **Lifecycle stage `DESCENDANTS_TERMINATED`** runs *before* the final-state capture that the git-tree-sovereignty and effect-ledger work makes load-bearing. It freezes the cgroup (so no new descendants are accepted), kills the whole owned tree, waits for confirmed extinction (`cgroup.procs` empty under a bounded wait), and verifies no surviving process holds a workspace handle by walking `/proc/*/fd` for the workspace path. Only then does final filesystem validation and the S1 tree capture run.
- **High-risk runs refuse outright** when no primitive is available (`NewScope` returns an error), per the same "refuse, not degrade" posture as `enforce.Supported()`. A medium/effectful tier-1 run degrades to the pre-v4 process-group behavior only if none of the three primitives qualify.

This closes the path Sol's report named (P0-4): a backend that `setsid`s + double-forks + delays a write cannot land that write into the live repo *seconds after* the run was approved, because the kill happens before the approval barrier, not after the main process exits.

## Git tree sovereignty

The merge/commit path is the one moment a governed run actually mutates the live repository, so it gets its own isolated plumbing layer (`internal/gitplumb`) rather than shelling out to `git add`/`git commit` in repository context:

- **No shell, ever.** Every git invocation is an `exec.Command` argv built from byte-exact arguments — never a shell string a hostile filename could reinterpret. `--literal-pathspecs` and `:(literal)` prefixes on every machine-generated path mean a file literally named `:(glob)**` stages only itself, not the whole tree.
- **Neutralized environment.** `GIT_CONFIG_GLOBAL=/dev/null`, `GIT_CONFIG_SYSTEM=/dev/null`, `GIT_CONFIG_NOSYSTEM=1`, an empty `core.hooksPath` directory, `commit.gpgsign=false`, `core.autocrlf=false`, `core.safecrlf=false`. Operator ambient state (a hostile global hooks path, a configured clean filter) cannot influence what gets committed. Blobs are hashed with `git hash-object -w --no-filters --literally` so attributes/clean/smudge filters never run.
- **Isolated temporary index.** `GIT_INDEX_FILE=<tmp>` outside any worktree — never `.git/index` — so a concurrently running backend cannot observe or mutate the merge tree mid-build.
- **Independent tree computation + commit-tree + update-ref CAS.** The expected tree is computed independently from the approved path set + blob hashes, `git write-tree` produces the candidate, mismatch = quarantine, `git commit-tree <tree> -p <parent>` produces the commit, `git update-ref` carries the expected old value as a compare-and-swap. A post-commit re-verification reads back the commit's tree and asserts it equals the approved tree — **approval is valid only when `approved_tree == committed_tree`**.
- **`.governator/` and `.codegraph/` are asserted absent** from the final tree rather than skipped, closing the pathspec-magic-filename exploit (P0-2). `git status --porcelain=v2 -z` (NUL-delimited, byte-parsed) replaces the human-readable v1 format that mangled hostile filenames (P1-9).

`baseline_tree`, `approved_tree`, and `commit_tree` are recorded in the run record. A hostile pre-commit hook cannot alter the committed tree or execute with Governator's authority, because no repository-context `git commit` is ever invoked.

## Executable identity

A backend's executable identity is resolved exactly once per run into an immutable `BackendExecutionHandle` (`internal/agents/handle.go`), built from a single open file descriptor: PATH lookup, symlink canonicalization, then one `os.Open` whose `fstat` and `io.Copy`-hash back every identity field (owner, mode, dev+inode, SHA-256) — never a second independent path read. Attestation, containment, replay identity, launch, and the audit record all consume that one handle (closing P0-6's "resolved twice" race).

Launch goes through `BackendExecutionHandle.VerifyUnchanged()` — an unconditional re-stat + re-hash immediately before `Start()` — in both the fd-launch (`/proc/self/fd/<n>` via `ExtraFiles`, layering on top for compiled binaries) and wrapper-launch (containment `Scope` / `systemd-run`) paths. Holding the fd open only protects against unlink+recreate; it does not protect against in-place truncate+overwrite, and for a *script* backend the kernel's shebang handling re-opens the path itself to find the interpreter, which sees the new bytes regardless. `VerifyUnchanged` is the actual TOCTOU fix (P0-6's deeper mechanism, found and fixed during S3).

`agents.BackendIdentity.Known()` requires operator-declared `Provider` + `ModelRevision` on `config.Backend` (not inferred from the backend name), folded into `ExecutionIdentity.Hash()`; `attest.VerifyHighRiskNative` hard-refuses an unknown identity before it even checks for a stored attestation. **This is a breaking config-schema change for existing high-risk-local / native-sandbox jobs:** `backends.<name>.provider` and `backends.<name>.model_revision` must be added to `config.yaml` or the run fails closed. Docker identity is the content-addressed image ID resolved from `docker image inspect` (P1-1), never the mutable tag; replay binds to the image as a whole.

## Trusted-tool registry

Every external controller tool — `git` today, and any operator-declared helper such as a context-graph provider — must have an explicit trust entry (`internal/toolregistry`: shipped default for `git`, or `~/.governator/tools.yaml`) before Governator will execute it at all. **Absence from the registry is "outside the trust model," not "trust whatever PATH finds."** A registered entry is independently re-verified on every resolution: canonical path, content hash, owner, mode, non-writable parent directories.

`git` self-pins on the first successful `gov doctor` run (`toolregistry.Pin`, trust-on-first-use mirroring SSH `known_hosts`); every later resolution reads that pinned file, never PATH, so a PATH change after the pin exists cannot redirect it. The `gitplumb` layer and the duplicated `shell()` helpers in `internal/runtime`/`internal/runner` route through that pinned path. `gov doctor`'s `checkGit` was rewritten to verify+auto-pin via the registry, and a new `checkToolRegistry()` audit reports which configured tools currently resolve as trusted. The context-graph provider (`codegraph`) is gated the same way: unregistered + `mode=auto`/`off` is silently disabled (never invoked); unregistered + `mode=required` is a hard error.

`agents.BuildAllowedEnv` filters the backend launch's inherited environment to a small fixed baseline (`PATH`/`HOME`/`LANG`/`LC_ALL`/`TMPDIR`/`TZ`/`XDG_RUNTIME_DIR`/`DBUS_SESSION_BUS_ADDRESS` — the last two required for `systemd-run --user --scope` to reach the session bus) plus the backend's own declared `AllowedEnv`. Cloud credentials, `GITHUB_TOKEN`, `SSH_AUTH_SOCK`, and unrelated provider keys are stripped by default. Only the variable-name set is hashed into `ExecutionIdentity.RunnerConfigHash`, never the values.

## Local external enforcement

For a `risk_class: high` job on `runner: local` without a signed override, Governator wraps the launch in its own kernel-enforced sandbox (`internal/enforce`):

- **Filesystem: Landlock LSM.** The launch goes through `gov __sandbox_exec` — Governator re-execs itself, applies a Landlock ruleset to *that* process (filesystem writes confined to the workspace, every other path read-only — or every path including the workspace under `ReadOnly`), then `syscall.Exec`s into the real backend. The restriction is already in force on the process that becomes the backend; it is not a wrapper the backend can out-race, and not a policy the backend can lie about honoring.
- **Network: a network namespace with no configured route.** When the contract denies network (`Network: false`, the default), the entire launch runs inside `unshare --net --map-root-user`. Inside that namespace every `connect()`/`bind()` past loopback fails at the kernel level — egress is structurally impossible, not merely denied by policy.
- **Process tree: cgroup v2 scope.** The same launch is wrapped by [descendant containment](#descendant-containment) so a `setsid` / double-fork / delayed-write child cannot survive the execution boundary. Approval is impossible without a recorded successful extinction proof.

`enforce.Supported()` reports whether this host can actually provide the layer (a usable Landlock ABI and the `unshare` binary). When `Supported()` is false, a high-risk local run **refuses outright** rather than silently producing an unconfined launch — the same "no primitive, refuse rather than degrade" posture as descendant containment. A medium/effectful tier-1 run follows the same rule when `containment.local_effectful_tiering` is at its default `enforce`.

The transcript is **demoted to explanatory evidence** under this model. Filesystem effects come from a worktree before/after diff (`changed`/`deleted`, ledgered since before v4); network egress is structurally impossible inside the netns rather than policy-denied; process creation counts come from the cgroup's own `cgroup.procs`. A discrepancy between the backend's self-reported `RESULT.json` and the externally measured effects surfaces as a `transcript_effect_mismatch` note; a discrepancy that is also out of scope is caught independently by the existing allowlist/forbidden/intended-writes checks on the external diff alone.

## Capability attestation lifecycle

Backend adapters (`internal/agents`) declare *expected* capabilities per adapter name — e.g. "Claude Code has a native sandbox." Before the Sol repair, any executable configured at `backends.<name>.bin` silently inherited that adapter's declared capabilities regardless of what the executable actually was. `internal/attest` records what an executable actually does under probe, but — after Sol redteam v4 P0-3 — **probe-observed behavior is evidence, not authorization** (see [Why a backend-attested native sandbox is not on this list anymore](#why-a-backend-attested-native-sandbox-is-not-on-this-list-anymore)):

- `gov attest <backend>` generates and stores an **attestation**: adapter name/version, the executable's canonicalized path and SHA-256, its `--version` output, the effective model ID, the effective config hash, and four probe results (supported flags, sandbox, network control, transcript format) — plus a 24-hour expiry. The attestation ID is a SHA-256 over all of that, stored in the ledger's `capability_attestations` table.
- A `risk_class: high` job on `runner: local` still resolves and records an attestation when the backend declares a native sandbox, and the matched attestation's ID still feeds `ExecutionIdentity` (so replay can't reuse an approval whose attestation has since changed or expired). What changed in v4: the attestation's verdict **no longer gates launch**. A failed or missing probe is no longer the launch-blocker it was pre-v4 — and a *passing* probe no longer authorizes the run. Launch authorization now requires `enforce.Supported()` (Governator's own external enforcement) or a signed override.
- Re-attestation is still required after any backend CLI upgrade or `backends.<name>.bin` repoint so the identity record stays accurate: a stale attestation mints a new `ExecutionIdentity` and invalidates prior replays, exactly as before.

## Docker hardening

`IsHardened()` requires every one of: a validated non-root `docker.user` (empty, `root`, `0`, and `0:0` are all rejected); `read_only_rootfs`; `cap_drop_all`; `no_new_privileges`; a digest-pinned image (`@sha256:` plus a real 64-hex digest — `allow_mutable_tag` is an explicit, logged exception and never makes a config "hardened," it only silences the digest requirement); and `network: deny`.

Hardening is **verified against the running container**, not just the declared request: for a hardened config, `DockerRunner.Observe` runs `docker inspect` and checks the container's effective user, network mode, read-only rootfs, capability drops, `no-new-privileges`, seccomp/AppArmor security profiles, running image digest, resource limits, and mount set against what was declared. `docker inspect` failing, or any mismatch, blocks approval for a hardened run — it does not degrade to a note the way it still does for a non-hardened, low-risk run.

Credential mounts resolve symlinks (checking both the raw and resolved path against a hardcoded Docker/containerd/CRI-O socket list before allowing the mount), require the resolved path to fall under a configured credential root, and by default only permit regular files — a directory requires an explicit `docker.credential_mount_allow_dirs` entry, and sockets/devices/FIFOs are never permitted regardless of configuration. Mounts land read-only under `/run/governator-credentials/`.

## Output byte caps (local and Docker)

Output byte caps are enforced for both runners. `docker.output_cap_bytes` bounds a Docker run's container stdout/stderr (`internal/runner/docker.go`'s `cappedWriter`); `local.output_cap_bytes` bounds a local run's host subprocess the same way (`internal/runner/runner.go`'s `LocalWorktreeRunner.executor`, closing Sol High 11). Both default to 20MiB, report accepted/discarded bytes through `Runner.Observe`, emit a loud `OUTPUT_TRUNCATED` ledger stage, and honor their runner's `require_complete_transcript` flag to quarantine a run on a capped transcript rather than approve it on an incomplete trail. Neither field participates in Docker/local's "must be absent under the other runner" placement rule crossing over — `docker.*` stays Docker-only, `local.*` stays local-only. See [docs/security.md](security.md), High 11.
